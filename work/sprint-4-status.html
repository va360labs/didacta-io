Contrato SandboxedSecrets + types + manifest schema SE-001
Hecho

Nuevo contrato análogo a ctx.db y ctx.jobs — el host inyecta un cliente de secretos cifrados scoped a (tenantId, moduleName) congelados en la closure. Cross-tenant / cross-module leak imposible por descuido del módulo.

Files:

apps/api/src/marketplace/sandboxed-secrets.types.ts (nuevo, ~190 LOC)
apps/api/src/marketplace/module-manifest.schema.ts (+ ~80 LOC para requiresSecrets + secretsLifecycle)

Decisiones no obvias:

  • list() NUNCA devuelve values — solo metadata. Si un módulo bugueado loguea el resultado de list(), no leakea credenciales.
  • Tres stubs: BlockedSandboxedSecrets (sin requiresSecrets), AnonymousSandboxedSecrets (route pública sin Bearer), real (con auth). Distinguir Anonymous de Blocked permite mensajes accionables distintos.
  • Caps duros del core: 256 keys/módulo · 64 KB/value · 128 chars/key. El manifest puede declarar caps más estrictos (defaults 32/8KB).

Trabajo Completado · Phases reales del ETL

Extract phase per-tick con cursor en progress JSONB ET-001
Hecho · entidades paginables

Reemplazado el STUB del case 'extracting' en onJobTick. Cada tick: lee cursor de progress JSONB, recupera appPassword vía ctx.secrets, fetch 1 página WP (max 100 items), UPSERT a stg_<entity>, avanza cursor. Cuando completed.length === EXTRACT_ENTITIES.length → tryTransition('extracting','transforming').

Entidades cubiertas (paginables vía WP REST): users · courses · lessons · topics · quizzes · groups.

Cursor shape persisten en BD:

{
  "phase": "extract",
  "current": "lessons",
  "page": 3,
  "completed": ["users", "courses"],
  "totalsPerEntity": { "users": 47, "courses": 12 }
}
Limitación documentada: entities "fan-out" (questions per-quiz, enrollments per-course, enrollments per-group, media derivada, progress por step) NO están incluidas. Requieren cursor de 2 niveles (parent → page) y N requests por parent — ver tarea diferida ET-001b abajo.
Transform phase per-tick con mappers existentes ET-002
Hecho · reusando mappers/*

Reemplazado el STUB del case 'transforming'. Cada tick: lee batch de N=100 filas con is_valid=FALSE de stg_<entity>, aplica el mapper apropiado (importado de ./mappers/index.js — los skeletons del orchestrator viejo se reutilizan acá sin reescribir), escribe canonical + is_valid=TRUE o validation_errors. Errores van a DLQ con phase='transform'.

Cursor: { phase: 'transform', current, completed[] }. Cuando un batch llega vacío para la entity actual → marca completed y avanza a la siguiente. Cuando todas completas → tryTransition('transforming','loading').

Mappers reusados: mapUser, mapCourse, mapLesson, mapTopic, mapQuiz, mapGroup. Returns MapResult<T> con ok + canonical o errorCode + errorMessage.

Load phase per-tick con ctx.didacta.upsertByExternalRef + DLQ ET-003
Hecho · con deuda

Reemplazado el STUB del case 'loading'. Cada tick: lee batch de N=50 filas válidas sin target_id, llama ctx.didacta.<entity>.upsertByExternalRef({ ...canonical, externalRef: { externalSource: 'learndash', externalId: source_id } }), escribe target_id. Errores tipados → DLQ con phase='load'.

Orden de carga: users → courses → lessons → topics → quizzes → groups.

Deuda 1 — quizzes shell-only: ctx.didacta.quizzes.upsertByExternalRef hoy NO persiste las questions inline (warning explícito en línea 1066 de sandboxed-didacta.service.ts). El shell se crea con externalRef y queda marcado como cargado; las questions persisten en stg_questions sin subir al core. Bloqueante: DD-006 (ver pendientes).
Deuda 2 — mapping entity → ctx.didacta namespace: el código asume que topics se cargan vía ctx.didacta.lessons (no hay tipo topic separado en el core) y groups vía ctx.didacta.enrollments. Ambos mappings son aproximaciones — el host probablemente rechaza canonical con unitType: 'topic'. Aparecerán errores en DLQ. El smoke real va a revelar la verdadera shape y habrá que ajustar el adapter inline.
Deuda 3 — canonical vs DidactaUpsertXInput shape: los mappers fueron escritos antes de finalizar ctx.didacta. Los canonical types (CanonicalUser etc.) NO necesariamente matchean DidactaUpsertUserInput etc. exactamente. Las primeras invocaciones del smoke darán DIDACTA_VALIDATION_ERROR que irán a DLQ. Aceptado conscientemente — el user pidió "solo smoke real" como estrategia de testing.
Reconcile phase + validation_reports ET-004
Hecho · single tick

Audit chain SHA-256 en audit_events ET-005
Hecho · 1 evento

Junto con ET-004, el case 'reconciling' calcula prev_hash = (SELECT hash FROM audit_events ORDER BY occurred_at DESC LIMIT 1), computa hash = SHA-256(stableStringify({ prevHash, body })), e inserta action='phase.completed' en mod_migrator_learndash_audit_events. Permite verificar integridad post-mortem en GET /jobs/:id/report.

La versión minimal funcional cierra el contrato (hash chain válido + verify-able) pero la granularidad real fina queda para una iteración posterior — añadir await appendAuditEvent(...) en cada batch del load phase + en cada tryTransition es ~5 calls extra distribuidas, mecánico.

Extract fan-out: questions per-quiz + enrollments per-course/group ET-001b
Diferido a Sprint 5

Qué falta: el extract phase actual procesa solo entidades paginables vía WP REST estándar. Las siguientes NO se extraen todavía:

  • questions — endpoint LD /wp-json/ldlms/v1/sfwd-quiz/<id>/questions requiere iterar primero los quizzes ya stageados y hacer una request por quiz.
  • enrollments directas — endpoint LD /sfwd-courses/<id>/users, requiere iterar courses ya stageados.
  • enrollments por grupo — endpoint LD /groups/<id>/users, requiere iterar groups ya stageados.
  • media — derivada de los featured_media de los course payloads, requiere fetch por id.
  • progress de usuario — no hay endpoint masivo en ldlms/v1; requiere iterar (user, course) pares.

Por qué no se hizo: el patrón de cursor para fan-out es distinto al de entidades paginables — necesita un segundo nivel { parentEntity, parentIdx, parentTotal, page }. Implementarlo bien sin smoke test previo es prematuro — el código actual de la simple extract phase ya tiene asunciones que el smoke va a desafiar. Mejor cerrar con la simple, smoke-test, y volver con fan-out cuando la base esté firme.

Impacto: en validation_reports estos entities aparecen con source_count=0. El usuario ve "0 preguntas migradas / 0 matrículas / 0 media" — explícito, no silencioso.

Riesgos sin verificar — el smoke real va a destapar

Schema drift Prisma
Riesgo
Si la BD de Easypanel ya tiene cambios manuales o si la migration anterior 20260506000001_add_external_id_to_core_resources no se aplicó (lo marcaba como pendiente el HANDOFF alpha.55), aplicar la nueva puede fallar.

Mitigación: antes de migrate deploy, correr pnpm prisma migrate status y resolver drift si lo hay.

Doble instancia de SecretCipherService
Riesgo bajo
AuthModule y MarketplaceModule ahora cada uno construye su propia instancia de SecretCipherService vía loadCipherKey(). Son criptográficamente equivalentes (mismo material de key) pero técnicamente son dos objetos.

Mitigación: si quisiera limpiar, exportar SecretCipherService desde AuthModule y dejar que MarketplaceModule lo importe. No urgente — la duplicación es funcional.

Mappers / canonical / DidactaUpsertXInput misalignment
Riesgo alto
Los mappers (mapUser, mapCourse, etc.) fueron escritos a priori (HANDOFF alpha.51), antes de finalizar ctx.didacta (alpha.52). El CanonicalUser tiene displayName + roles pero DidactaUpsertUserInput probablemente usa name + un solo role o algo distinto.

Mitigación: el smoke real va a tirar DIDACTA_VALIDATION_ERROR en el primer batch del load phase. Esos errores van a DLQ (no crashean el job). Después de revisar la DLQ, ajustar inline un adapter canonicalToDidactaInput(entity, canonical) en index.ts.

Tests de SE-002 NO escritos
Deuda
El DoD original de SE-002 incluía tests unitarios cubriendo: set new, set update, get-not-found, get-expired, delete, list, quota exceeded, key invalid, value too large.

Por qué no: tu directiva "Solo smoke real, sin unit tests nuevos". Documentado conscientemente. Cuando aparezcan bugs reales del smoke, tests de regresión van a hacer falta.
