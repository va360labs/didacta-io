Hipótesis ordenada por probabilidad

H1 — Storage blob de la BD apunta al ZIP de 1.0.14 (sin dist/ui/) · muy probable

El controller llega a la línea 74 (módulo SÍ está en installed_module con status=INSTALLED), pero el ZIP que descarga de storage no tiene dist/ui/admin.js dentro. Causas posibles:

  • El upload de 1.0.15 al marketplace falló silenciosamente y la BD sigue apuntando al ZIP de 1.0.14.
  • El install pipeline detectó "misma versión" y no reemplazó el storage (cuesta creer que vea 1.0.14 vs 1.0.15 como "misma", pero hay que descartar).
  • El usuario subió el ZIP firmado de una alpha anterior (1.0.13, 1.0.14) en lugar del 1.0.15.

Cómo descartar:

SELECT version, status, package_storage_key, package_sha256, installed_at, updated_at
  FROM installed_module
 WHERE name = 'mod.migrator-learndash';

Si version != '1.0.15' → confirmado H1, la instalación no entró. Si version = '1.0.15', descargar manualmente el blob package_storage_key y correr unzip -l: tiene que aparecer dist/ui/admin.js (~40 KB) — si no, el ZIP que llegó a storage está corrupto/desactualizado.

SHA del ZIP local de referencia: el último firmado en este repo es dist/mod.migrator-learndash-1.0.15.zip. git status está limpio post-commit cfa4a0e. Para sacar el SHA-256 local: sha256sum dist/mod.migrator-learndash-1.0.15.zip.

H2 — El install pipeline del host no preserva subdirectorios del ZIP · posible

El controller ModuleAssetsController.getUIBundle() en alpha.60 lee el ZIP completo desde storage por cada request. Esto requiere que el ZIP original esté íntegro en storage. El install pipeline NO unzipea — solo guarda el blob.

Sin embargo, si en alguna iteración pasada se cambió el flujo a "extraer y guardar archivos sueltos", la lectura via zip.getEntry(...) daría null porque el blob no es un ZIP.

Cómo descartar:

SELECT pg_typeof(package_storage_key), package_storage_key, package_size_bytes
  FROM installed_module WHERE name = 'mod.migrator-learndash';

Si package_size_bytes coincide con el del ZIP local (~165 KB), el blob completo está. Si es mucho menor, hay un problema de pipeline.

H3 — In-memory cache del controller sirviendo bundle viejo · improbable pero check rápido

Línea 20 del controller: const bundleCache = new Map<string, ...>() en memoria. Solo cachea hits exitosos (línea 64-70), NO cachea 404s. Por eso este no debería ser el problema (al user le da 404).

Pero si el operador hizo restart del container DESPUÉS del install, el cache está vacío y el 404 viene del ZIP real. Si el operador NO reinició entre installs múltiples, podría haber estado mostrando bundles viejos (cache hit). Para descartar 100%: restart del API + intentar.

H4 — El módulo está instalado pero con status != 'INSTALLED' · descartado por mensaje

El controller tira un error DIFERENTE en línea 78-81 si status != INSTALLED. El mensaje que ve el user es el de línea 99-100 → el módulo PASÓ ese check. Solo confirmar con la SELECT de H1 que status = 'INSTALLED' y no FAILED/DEPRECATED.
