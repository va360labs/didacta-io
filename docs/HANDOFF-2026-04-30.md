## 3. Decisiones arquitectónicas tomadas (con rationale)

### 3.1 Patrón Dockerfile: 5 stages con runner desde alpine LIMPIO

```
base → fetcher → builder → pruner → runner
```

**El runner NO hereda del builder** (`FROM node:22-alpine AS runner`). Si heredase, las layers intermedias del builder (devDeps, caches turbo, .tsbuildinfo) seguirían en la imagen final aunque el filesystem las borrase. Una imagen Docker es la SUMA de sus layers, no un snapshot.

El stage `pruner` deja el repo runtime-only y el runner hace un único `COPY --from=pruner` que crea una sola layer.

Esto se descubrió cuando el primer intento (runner FROM builder + alpine) subió la imagen a 3.12GB.

### 3.2 Trampas de Alpine documentadas en el Dockerfile

- `apk add --no-cache --virtual .build-deps g++ make python3` en builder para compilar `argon2` contra musl. Borrar en pruner.
- Runtime apk: `bash` (entrypoint usa bashismos `[[`, arrays, `wait -n`), `openssl`, `curl`, `postgresql16-client`, `libc6-compat`, `tini`.
- `tini` en alpine: `/sbin/tini` (no `/usr/bin/tini` como en Debian).
- `addgroup -S` / `adduser -S` (BusyBox), no `groupadd`/`useradd`.
- `ENV CI=true` también en builder (no solo pruner): `pnpm` aborta `node_modules` rebuild sin TTY si `.npmrc` o lockfile cambian.

### 3.3 Soporte de packages para runtime --prod

- **`.npmrc` con `shamefully-hoist=true`**: workspace packages (`@didacta/license-sdk`) declaran `@nestjs/common` como peer **optional**. En dev funciona por hoist agresivo; con `pnpm install --prod` los packages no resolvían sin hoist. La fix correcta sería quitar `optional: true` o mover a deps directas, pero hoist es más simple y aceptable.
- **`packages/database/package.json`**: `prisma` CLI movido de devDeps a deps. El entrypoint corre `prisma db push` en runtime, así que el CLI debe sobrevivir al `--prod` prune.
- **`packages/database/prisma/schema.prisma`**: `binaryTargets = ["native", "debian-openssl-3.0.x", "linux-musl-openssl-3.0.x"]`.
- **`apps/web/next.config.ts` → `next.config.mjs`**: Next 15 carga el config en runtime y exige `typescript` si es `.ts`. Como TS es devDep purgada en runner, el config debe ser plano JS/MJS.

### 3.4 Trampa del tsbuildinfo (MIG-059)

`tsconfig.base.json` tiene `incremental: true` y tsc genera `*.tsbuildinfo` por package. Si esos ficheros entran al contexto Docker (con `COPY . .`), tsc usa la cache y NO emite `dist/`. El build "pasa" con exit 0 pero los `.d.ts` y `.js` no existen.

**Defensa doble en repo**:
1. `.dockerignore` con `**/*.tsbuildinfo` (el patrón root no matcheaba nested).
2. `RUN find . -name "*.tsbuildinfo" -not -path "*/node_modules/*" -delete` en builder.

NUNCA poner `composite: true` en tsconfigs de packages — fuerza `tsc --build` y `tsc -p` deja de emitir.

### 3.5 Hot-spots eliminados en pruner

- `apps/web/.next/cache` (~200MB de cache de webpack, no se usa en runtime).
- `apps/e2e` (no se ejecuta en producción).
- `tsconfig*.json`, `vitest.config.*`, `eslint.config.*`, `*.tsbuildinfo`.
- `src/`, `tests/`, `__tests__`, `.turbo` en todos los workspace packages.

## 4. Backlog priorizado — qué hacer en esta nueva sesión

El usuario pide reducir aún más la imagen (1.3GB sigue pareciéndole mucho). Hay tres palancas reales por orden de **ROI / riesgo**.

### Opción A — Auditar deps innecesarias [HACER PRIMERO]

**Tiempo**: ~2h. **Riesgo**: bajo. **Diff esperado**: -150-300MB → ~1.0-1.15GB.

1. **Prisma binaryTargets**: hoy hay `["native", "debian-openssl-3.0.x", "linux-musl-openssl-3.0.x"]`. En la imagen final SOLO se usa musl. Cambiar a SOLO `["linux-musl-openssl-3.0.x"]` para producción y dejar los otros para dev. Diff: ~100MB (cada binary engine de prisma pesa ~30-40MB).
   - Cambio en `packages/database/prisma/schema.prisma`.
   - Hay que tener cuidado: `db:generate` en dev local (no-musl) necesita `native`. Solución: variable `PRISMA_BINARY_TARGETS` o múltiples schemas.
2. **`@aws-sdk/client-s3` + `@smithy/*`** (~150-200MB de node_modules). Hetzner/MinIO no necesitan el SDK completo de AWS. Reemplazar por `minio` SDK (~5MB). Tocar:
   - `apps/api/src/storage/*.ts` (imports + clase StorageService).
   - `apps/api/package.json`: quitar `@aws-sdk/*`, añadir `minio`.
   - Tests de storage.
3. **`pino-pretty`** está en runtime deps de api (`apps/api/package.json` línea 53). En prod solo se usa JSON. Mover a devDeps. Diff: ~5MB pero higiene.
4. **`qrcode` + `otplib`** se usan solo en MFA. Si MFA está detrás de capability gate, importables dinámicamente. Diff: ~10MB.

### Opción B — Next.js standalone [HACER DESPUÉS DE A]

**Tiempo**: ~1h. **Riesgo**: medio. **Diff esperado**: -250-400MB → ~700-900MB.

1. Activar `output: 'standalone'` en `apps/web/next.config.mjs`.
2. Configurar `outputFileTracingRoot: path.join(process.cwd(), '../..')` para que Next trace correctamente las deps de workspace packages en el monorepo.
3. En el `pruner` del Dockerfile: en lugar de copiar `apps/web/.next/` entero, copiar `apps/web/.next/standalone/` (que ya incluye un mini node_modules con solo lo que el web usa) + `apps/web/.next/static/` + `apps/web/public/`.
4. Cambiar `infra/docker/entrypoint.sh` para arrancar web con `node apps/web/.next/standalone/apps/web/server.js` en lugar de `next start`.

**Gotchas**: standalone en monorepo tiene rutas relativas peculiares en `server.js`. Hay que verificar paths con un test build local antes del Dockerfile.

### Opción C — Separar api/web en dos imágenes [DESCARTAR POR AHORA]

**Tiempo**: ~3-4h. **Riesgo**: alto. **No compensa** mientras Easypanel use mono-contenedor. Reservar para cuando se vaya a Hetzner/Kubernetes con pods separados (Sprint posterior).

### Opción D — Eliminar node_modules de la imagen [USUARIO PROPUSO; DESCARTADO]

**Razones**: rompe inmutabilidad Docker, primer arranque baja ~1GB de npm, argon2 requiere toolchain de compilación en runtime, depende de internet en arranque, crashloop = re-installs. Rationale completo en la conversación de la sesión anterior. **NO HACER**.
