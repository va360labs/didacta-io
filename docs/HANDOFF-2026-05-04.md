## 3. Decisiones arquitectónicas tomadas en esta sesión

### 3.1 Sidebar = Variante D del design-system (rail + panel)

Reemplazo el sidebar plano por un layout de dos columnas:
- **Rail 72px** (izq): brand top + lista de áreas con icono+label corto + avatar al fondo con popup de cuenta (Perfil / Seguridad / Suscripciones / Cerrar sesión).
- **Panel** (der): header del área + lista de items + footer con conteo.
- **Detección automática** del área activa según pathname (matchea href más largo).

Re-agrupación admin: el bloque único "Administración" se sub-divide en 4 áreas separadas: **Tenant** / **Seguridad** / **Integraciones** / **Facturación**. "Mi cuenta" sale del sidebar y vive en el popup del avatar.

Ref visual: `D:\Test\learnship\docs\design-system\sidebar\VariantD.modules.jsx`.

### 3.2 Sidebar persistente en páginas con scroll: `sticky top-0 self-start h-dvh`

El padre del shell tiene `min-h-dvh` (crece con el contenido) pero el sidebar tenía solo `h-dvh` (altura del viewport). En páginas largas quedaba un hueco visible debajo. Fix: `sticky top-0 self-start h-dvh` mantiene el sidebar pegado al viewport mientras el main scrollea.

### 3.3 Filtrado de items por módulos activos del tenant

Nuevo endpoint `GET /api/v1/me/modules` (en `MeModulesController`, vive en `ModulesModule` para evitar ciclo con `AuthModule`). Devuelve `{ activeModules, enabledCapabilities }` en una sola llamada.

`SidebarItem.requiresModule?` opcional. `filterByActiveModules()` oculta items cuyo módulo no está activo y elimina grupos vacíos. **No confundir** con capabilities EE: estas siguen el patrón EeGate (visible-pero-bloqueado, ver `docs/UI-EE-GATING.md`).

### 3.4 Refresh tiempo real del sidebar (defense-in-depth)

Dos capas:
1. **Re-fetch al cambiar pathname**: useEffect depende de `[pathname]`. Cualquier navegación dentro del shell refresca activeModules.
2. **Evento custom `didacta:modules-changed`**: `/admin/configuracion` lo dispatcha tras cada toggle exitoso. El layout escucha y re-fetch al instante.

### 3.5 Módulos `category: 'core'` no se pueden desactivar

8 módulos viven en `modules/*` por estructura del repo pero son arquitectónicamente parte del producto base: `mod.theming`, `mod.courses`, `mod.learning`, `mod.certificates`, `mod.assessments`, `mod.community`, `mod.billing`, `mod.subscriptions`.

Implementación:
- `TenantModuleListItem.isCore` (computado de `manifest.category === 'core'`).
- `TenantModulesService.disable()` rechaza con `CORE_MODULE_NOT_DISABLEABLE` (HTTP 422).
- `ModuleRegistryService.healCoreModulesEnabled()` corre tras boot: re-habilita filas `tenant_module` donde un módulo core esté `enabled=false` (auto-corrige tenants en mal estado).
- Frontend `/admin/configuracion` filtra items con `isCore=true` — solo muestra los opcionales (zoom-live, fundae, ai-tutor, ai-grader, ai-content, hello-world).

### 3.6 Listings cross-tenant `/super/users` (PR #39)

Endpoint gateado por rol `super_admin` + capability `feat:multi_tenant.real`. Sin licencia EE → 402. Filtros: search, status, role, tenantId, paginación. Plan completo de RLS strict en `docs/RLS-STRICT-PLAN.md` (NO ejecutar hasta `0.0.1-beta.1`).
