## 3. Decisiones arquitectónicas tomadas en esta sesión

### 3.1 Setup wizard como módulo CORE público (no script CLI)

`SetupModule` en `apps/api/src/setup/` con dos endpoints públicos sin auth:
- `GET /api/v1/setup/status` — barato, retorna `{ initialized }` contando tenants `deletedAt: null`.
- `POST /api/v1/setup/init` — idempotente. Re-chequea `tenantsCount > 0` DENTRO de la transacción para cerrar la ventana de carrera. Devuelve tokens firmados (auto-login).

**Por qué no un script CLI**: el operador típico de self-host en Easypanel/Coolify no tiene acceso conveniente a `docker exec`. La UX correcta es "abrí la URL y completá el wizard".

**Por qué seguro a pesar de ser público**: los tenants nunca se hard-deletean (solo `deletedAt`). Una vez creado el primer tenant, el endpoint queda permanentemente cerrado con 409.

### 3.2 Matcher de middleware Next.js: explícito, no catch-all

La primera versión usaba la receta canónica de los docs (`/((?!_next/static|_next/image|...).*)`), que captura rutas internas como `_not-found` y romper el routing en Next 15. Cambiada a una lista explícita de rutas:

```ts
matcher: ['/', '/signin', '/signup', '/forgot-password', '/reset-password']
```

Con esto el middleware solo intercepta los puntos de entrada al login, evitando colisiones con cualquier mecanismo interno de Next.

### 3.3 Pruner del Dockerfile DEBE excluir `.next` y `node_modules`

El antiguo:
```dockerfile
find apps packages modules -type d \( -name src ... \) -prune -exec rm -rf {} +
```
borraba `apps/web/.next/server/src/`, donde Next 15 compila el middleware cuando vive en `src/middleware.ts`. El runtime arrancaba pero el middleware-manifest apuntaba a un fichero inexistente y todas las rutas con matcher devolvían 404.

Fix:
```dockerfile
find apps packages modules -type d \
  \( -name node_modules -o -name .next \) -prune \
  -o -type d \( -name src -o -name tests ... \) \
  -print -exec rm -rf {} +
```

Documentado en el Dockerfile con comentario explicativo.

### 3.4 Aplanar `(setup)` route group → `app/setup/`

Next 15 tiene comportamientos sutiles cuando un route group "raíz" (`(setup)/` con su propio `layout.tsx`) coexiste con otros groups (`(app)/`, `(auth)/`). Para evitar problemas, la página vive como `app/setup/page.tsx` con su propio `layout.tsx`. Funcionalmente idéntico, más predecible.
