## 3. Decisiones arquitectónicas tomadas en esta sesión

### 3.1 Listings cross-tenant: namespace `/super/*`, no `/admin/*`

Elegí `GET /api/v1/super/users` (no `/admin/users/all` ni `/admin/users?cross_tenant=true`) por:

- **Separación semántica clara**: `/admin/*` siempre es tenant-scoped (filtrado por `u.tenantId` del JWT). `/super/*` ignora ese filtro y opera global.
- **Auditoría**: rutas `/super/*` son trivialmente filtrables en logs / WAF para tratamiento especial.
- **No frágil con el módulo del registry**: cualquier middleware que lea el path detecta `super` y aplica controles extra.

El controller vive en `apps/api/src/admin/super/super-users.controller.ts` (carpeta dentro de `admin/` por proximidad organizativa, no por compartir tenant scope).

### 3.2 Gates en orden estricto: rol primero, capability después

Orden en `SuperUsersController.list`:

1. `JwtAuthGuard` — sesión válida (else 401).
2. `requireSuperAdmin(user)` — rol `super_admin` estricto, NO `tenant_admin` (else 403).
3. `license.requireCapability(MULTI_TENANT_REAL)` — dentro del service, antes de tocar Prisma (else 402 vía `LicenseExceptionFilter`).

Razonamiento: 401 < 403 < 402. No exponemos el gate de capability a usuarios sin rol válido (evita user enumeration de roles vía 402 vs 403).

### 3.3 Filtro `role` post-fetch (limitación documentada)

`SuperUsersService.list` aplica `role` filter en JS tras obtener filas de Prisma. Razón: el join sobre la tabla pivote `user_roles` complicaría el `where` y la paginación pre-rol seguiría dando un total impreciso. Documentado en el código + test.

Si el volumen de users crece (>50k) o se necesita total exacto post-rol, conviene migrar a query SQL custom.

### 3.4 RLS strict no-ejecuta en alpha

Hallazgo (verificado vía SQL en didacta-postgres): el rol `didacta` que usa Prisma en runtime tiene `BYPASSRLS=t + SUPERUSER=t`. Las policies `tenant_isolation` definidas en `packages/database/prisma/rls.sql` **NO enforzan a nivel BD**. El aislamiento por tenant es lógico (filtros `WHERE tenantId=X` en código).

Para holdings con varias filiales en EE, esto debería migrarse a un rol `didacta_app` no-superuser. Plan completo en `docs/RLS-STRICT-PLAN.md` (5 fases, 3.5-4.5 días estimados). Decisión: NO ejecutar en alpha — activar antes de `0.0.1-beta.1` o cuando haya cliente EE con licencia `feat:multi_tenant.real` real.
